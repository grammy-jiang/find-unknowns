## Problem Statement

Working with strong coding agents, output quality is bottlenecked by the user's ability to
discover and resolve their own unknowns — the gap between the prompt/context ("map") and the
real codebase and constraints ("territory"). Unknowns surface **before, during, and after**
implementation, but the tooling our landscape scan (2026-07-23) found only addresses the
*before*: interview/clarification skills cover known-unknowns at planning time, and the 2026
Spec-Driven Development wave (Spec Kit, Kiro, OpenSpec, BMAD…) snapshots known-knowns into an
upfront spec that goes stale the moment the agent hits territory the map missed. We found no
tool that classifies unknowns by kind, routes each kind to the technique that resolves it,
tracks them across the feature lifecycle, or verifies at the end that the human understands
what shipped.

`find-unknowns` is a Claude Code skill (files also installable for Codex and Copilot; see
Platform scope) built from the technique catalog in Thariq's essay "A Field Guide to Fable:
Finding Your Unknowns" (paraphrased and credited — see Constraints). It maintains a
per-feature **unknowns ledger** that every phase reads and writes.

## What Makes This Cool

Your unknowns become a tracked, closable thing — like TODOs, but for what you *don't know*:

- The **blindspot pass** populates the ledger; entries are classified by quadrant and routed
  by an explicit table (below) to the technique that resolves that kind of unknown.
- During implementation, a **deviation rail** appends entries when reality contradicts the
  plan, instead of the agent silently pivoting — persisted by a planted, user-consented
  pointer block so it survives fresh sessions (mechanism below).
- At the end, a **quiz is generated from the ledger** and appended to it; the human passes it
  before merging. The loop closes.

One artifact threads all three phases. A spec is a photograph; the ledger is a flight recorder.

### Definitions used throughout

- **Gate** — the skill withholds a specific artifact or statement while a condition is
  unmet and says exactly why; it never blocks the user, who can always insist or proceed
  manually (*advisory-with-teeth*). Each gate below names exactly what it withholds.
- **Ledger** — one markdown file per feature (contract under Recommended Approach).
- **Plant** — a delimited managed block the skill writes (with explicit in-session user
  consent) into `CLAUDE.local.md` so the deviation rail binds future sessions.

## Constraints

1. **Totally independent.** No runtime dependency on socratic-method or subagent-factory.
   May describe interview-style questioning generically; must work with none of the user's
   other tools installed.
2. **Rights: distillation-only source.** The source essay is copyrighted (Thariq [@trq212],
   "A Field Guide to Fable: Finding Your Unknowns", 2026-07-04,
   https://x.com/trq212/article/2073100352921215386). SKILL.md and references paraphrase and
   restructure; no verbatim passages; a Credits section in the README and SKILL.md
   attributes the technique catalog to the essay. Claims must not be stronger than the
   source ("when facing many unknown-unknowns, run a blindspot pass" — not "always run
   one"). **Keeping the original close** (maintainer request): `references/source.md` ships
   the full citation, the URL, and a distilled outline of the essay — but NOT the full text;
   vendoring the whole copyrighted article in a public package would be redistribution. The
   maintainer's personal full-text copy lives in gitignored `notes/`. If the author grants
   written permission, `source.md` may flip to include the full text with a license note.
3. **Architecture by copy, not dependency.** The package copies and adapts socratic-method's
   proven *scaffolding*: data-driven installer `PLATFORMS` dict, hardening patterns (byte
   cap, no-alias YAML loader, never-raise validator contract), golden-fixture discipline,
   eval-harness shape, CI shape, version-in-`__init__.py` release flow. The validator *core*
   and one eval capability are new development (see Feasibility notes). Deliberate
   duplication across the two repos is accepted; they may drift.
4. **Inherited maintenance rule.** A behavioral failure is not fixed until something durable
   changes — a grader, a scenario, or a rail in SKILL.md — never a prose spot-fix alone.
   Corollary: any behavioral property this doc asserts (e.g. the anti-gaming ordering) must
   have a grader; unasserted-by-grader properties are not yet real.
5. **Toolchain parity with the blueprint.** Python ≥3.11, `uv`, pytest, pre-commit (LF, one
   final newline, no markdown formatter — SKILL.md must never be reflowed by tooling), evals
   never wired into CI.
6. **PyPI name `find-unknowns` is free** (checked 2026-07-23; HTTP 404 on the JSON API).

### Platform scope (v1)

- **Claude Code:** full lifecycle (pre / during / post). During-phase persistence uses the
  plant (below), written to `CLAUDE.local.md` — uncommitted by convention, so it never binds
  collaborators or CI to a per-machine ledger path.
- **Codex and Copilot:** pre + post in v1. Persistent-instruction mechanisms exist on both —
  AGENTS.md (Codex; also read by the Copilot coding agent) and repository custom
  instructions `.github/copilot-instructions.md` / path-scoped `.github/instructions/*`
  (Copilot) — but those files are **committed and team-shared**; v1 deliberately declines to
  have a skill auto-edit shared instruction files (a consent problem: the plant would bind
  teammates who never opted in). Documented future work: an opt-in `--team-plant` that
  writes those files via a reviewed commit. The README states all of this plainly.

## Premises

1. **Lifecycle, not just planning.** Unknowns surface before, during, and after
   implementation; planning-time-only artifacts structurally miss the last two phases. This
   lifecycle coverage — not better questioning — is find-unknowns' reason to exist. *(agreed)*
2. **The ledger pays its rent.** The per-feature ledger is worth its ceremony only because it
   compounds: the blindspot pass populates it, deviations append to it, the quiz is generated
   from it. If updating stops mid-feature in practice, the design must shrink. *(agreed)*
3. **Dogfood-first.** The maintainer is user #1; success criteria come from real use on
   subagent-factory / socratic-method work before promoting to others. *(agreed)*
4. **Independence by copy, not dependency.** Adapt the socratic-method architecture by
   copying into the new repo; accept installer drift as the price of independence. *(agreed)*
5. **Distill, don't quote.** Paraphrase with attribution; never verbatim; no overclaiming
   beyond the source's hedged advice. *(agreed)*

## Approaches Considered

### Approach A: Single-skill monolith (minimal viable)
- Summary: One SKILL.md containing the diagnostic, all 8 techniques inline, and ledger
  conventions; markdown ledger with YAML frontmatter; schema + validator + adapted installer.
- Effort: S-M · Risk: Low
- Pros: fastest to dogfood; closest to the blueprint's shape; one file to reason about.
- Cons: every invocation pays tokens for all 8 techniques; techniques stay shallow; editing
  one technique risks the whole body; brittle as it grows.
- Reuses: installer `PLATFORMS` dict, validator scaffolding/hardening, eval harness shape,
  CI/release workflows.

### Approach B: Hub + technique references (ideal architecture) — CHOSEN
- Summary: SKILL.md is a thin router (intake, dispatch rule, routing table, ledger rules,
  deviation rail, quiz gate); each technique lives in `references/<technique>.md`, loaded
  only when routed to (progressive disclosure). Ledger is `unknowns-ledger-v1` (contract
  below). Quiz generated from ledger entries and appended to the ledger.
- Effort: M-L · Risk: Med-High (two items are new development, not ports: the entry-parsing
  validator core and the fixture-seeded eval capability — see the eval plan's honesty notes).
- Pros: token-efficient; techniques independently improvable and testable; versioned schema
  enables lockstep-edit discipline; technique #9 later is additive.
- Cons: more files; router misclassification is a new failure mode requiring eval coverage.
- Reuses: A's scaffolding reuse, plus the lockstep-edit rule (schema / SKILL.md template /
  validator / golden fixture / graders move together).

### Approach C: Ledger-first CLI (creative/lateral)
- Summary: A `find-unknowns` CLI owns all ledger writes (`init/add/resolve/log-deviation/
  quiz-source`); SKILL.md instructs the agent to call it; format drift impossible.
- Effort: L · Risk: Med-High
- Pros: strongest determinism; ledger usable by any agent or human outside Claude Code.
- Cons: heaviest build; shelling out is less portable across platforms with different tool
  grants; front-loads machinery before the loop is proven (violates the spirit of premise 2).

### The ledger contract (`unknowns-ledger-v1`)

**Location & discovery.** Ledgers live at `notes/unknowns/<feature-slug>-YYYYMMDD.md`
(gitignored by default — privacy-safe, mirroring the blueprint; committing is a documented
user choice). The filename slug MUST equal frontmatter `feature` (validator-enforced). On a
same-day recreate collision the router refuses and appends a `-b`, `-c`… suffix. Discovery
on invocation: the newest **active** ledger whose `feature` matches the conversation's
topic; **when in doubt, always list-and-ask — never silently create while ≥1 active ledger
exists.**

**Parsing contract** (new validator code; blueprint hardening patterns carry over — size
cap, no-alias YAML loading, never-raise findings, pinned error wording under mutation
tests):

- Frontmatter: YAML, validated against the JSON schema.
- Entries: body sections matching exactly `^## UNK-\d{3}$`, each parsed as a bullet
  key-value list of **bare values** (the annotations in the example below are illustrative
  only; the parser does not strip comments, and the golden fixture carries bare values).
- **Near-miss policing:** any `##` header beginning with `UNK` (case-insensitive) that fails
  the exact pattern is a validator finding. The only legal non-entry `##` headers are
  `## Quiz — attempt N`.
- Field rules: enums enforced; ids unique and ascending; ≥1 entry; `resolution` required on
  `resolved` and `deviated` entries; `risk` (rationale) required on `accepted-risk` entries
  (it is the quiz-judging basis for them); `technique` MUST be absent on `accepted-risk`
  and `deviated` entries (no technique is routed to either), MAY be absent on `abandoned`
  and not-yet-routed `open` entries, and is otherwise one of
  `interview | reference-hunt | brainstorm-prototype`.
- Cross-field rules: `quiz_passed: true` ⇒ `quiz_attempts ≥ 1` ∧ ≥1 quiz section ∧
  `status: complete` ∧ zero `open`/`investigating` entries.

```markdown
---
schema: unknowns-ledger-v1
feature: auth-provider-oauth
created: 2026-07-23
updated: 2026-07-23          # maintained by the skill on every write
status: active               # active | complete | abandoned
quiz_passed: false
quiz_attempts: 0
---
## UNK-001
- quadrant: known-unknown    # known-unknown | unknown-known | assumption
- origin: skill              # user | skill | deviation
- impact: architecture       # architecture | local | cosmetic
- status: resolved           # open | investigating | resolved | deviated | accepted-risk | abandoned
- technique: interview       # interview | reference-hunt | brainstorm-prototype (optional)
- statement: Which token-refresh strategy fits our session model?
- resolution: Sliding refresh; decided in interview 2026-07-23.
```

Unknown-unknowns never sit in the ledger as a quadrant: by definition, once written they are
known. The blindspot pass *surfaces* them; each surfaced item is immediately classified as
`known-unknown` or `assumption` with `origin: skill`. (`assumption` is first-class —
borrowing the classical PM assumption-log ancestry: an assumption is an unknown wearing
confidence.) `impact` exists so the pre-phase gate is implementable and gradeable. `origin`
is deliberately minimal (`user | skill | deviation`): `deviation` is load-bearing for the
rail and its graders; the other two record provenance without ceremony.

### The routing table (normative; lives in SKILL.md)

| # | Quadrant | Selector (decisive) | Primary technique |
|---|---|---|---|
| 1 | known-unknown | the user holds the answer | interview |
| 2 | known-unknown | the codebase/world holds the answer | reference-hunt |
| 3 | known-unknown | nobody holds it yet (open decision) | brainstorm-prototype |
| 4 | unknown-known | an exemplar exists in reachable code/artifacts | reference-hunt |
| 5 | unknown-known | no exemplar — "I'll recognize it when I see it" | brainstorm-prototype (variations to react to) |
| 6 | assumption | testable against existing code/data | reference-hunt (verify) |
| 7 | assumption | testable only by building something | brainstorm-prototype (spike) |
| 8 | assumption | too expensive to test now | **no technique** — status transition to `accepted-risk` (record `risk:`), monitored by the deviation rail |

Every (quadrant, selector) pair maps to exactly one primary technique; row 8 is explicitly a
status transition, not a technique, and is evaluated FIRST for assumptions — it overrides
rows 6–7 whenever the test is judged too expensive now. The blindspot pass is a *populating* technique only — it
never appears as a route for an existing entry. `implementation-plan`, `deviation-log`,
`explainer-pitch`, and `quiz` are phase-bound (pre-gate, during, post, post), not
quadrant-routed. **Degradation rail:** if a routed reference file is absent (partial
install), SKILL.md instructs: improvise the technique inline and add a note bullet to the
entry — never silently skip.

### Dispatch rule (how the router picks a phase)

1. `quiz` argument → **post** (quiz flow). Discovery widens for `quiz` only: newest
   *active* matching ledger, else newest *complete* matching ledger (recorded retake
   offer; attempts increment; an already-earned `quiz_passed: true` is never demoted by a
   later failed retake — verdicts are recorded, history stands).
   1a. `quiz` with no ledger of either status → explain, offer pre-phase.
2. No discoverable active ledger (none at all, or only `complete`/`abandoned`) → **pre**
   (intake → blindspot pass → classify → route; new ledger, collision rule above).
3. Active ledger exists → **during-resume**: status review, route still-open entries, log
   any deviations discussed, offer the quiz gate if implementation is done.

Staleness (advisory note in the router, not a normative gate — normative only if dogfood
shows ledgers actually rot): if the discovered active ledger's `updated` is ≥14 days old
with open entries, suggest resolve-or-abandon before proceeding; abandonment sets ledger
`status: abandoned` and cleans the plant.

### The plant (during-phase persistence, Claude Code)

At pre-phase go-ahead the skill **asks the user**, then writes one delimited managed block:

```text
<!-- find-unknowns:BEGIN -->
Unknowns ledger(s) for in-flight features (managed by find-unknowns; do not hand-edit):
- notes/unknowns/auth-provider-oauth-20260723.md
On any forced deviation from the plan: take the conservative option, append a `deviated`
entry to the ledger above, and keep going. Entry format — copy the shape of existing
`## UNK-` entries exactly, using the next ascending three-digit id:

## UNK-<next-id>
- quadrant: assumption
- origin: deviation
- impact: <architecture | local | cosmetic — your judgment; local when unsure>
- status: deviated
- statement: <what the plan assumed>
- resolution: <what reality forced instead, and the conservative option taken>

If the ledger path does not exist on this machine, this instruction is inert.
<!-- find-unknowns:END -->
```

- Target: `CLAUDE.local.md` (uncommitted by convention) — never the committed CLAUDE.md, so
  the plant can't bind collaborators or CI (whose machines lack the gitignored ledger).
  Note: `CLAUDE.local.md` is deprecated-but-honored in current Claude Code memory docs; if
  it stops loading, the documented fallback is an import line in a memory file pointing at
  an uncommitted planted file (e.g. `@notes/unknowns/plant.md`).
- **Hygiene:** the block is updated in place (never duplicated) and lists only `active`
  ledgers. Quiz-pass and abandon flows rewrite it; the post flow's last act is plant
  cleanup (block removed when no active ledgers remain).
- **Tool grant & policy:** the plant requires Edit/Write scope on `CLAUDE.local.md`, named
  in SKILL.md's `allowed-tools`. The plant is the *deliberate, user-consented exception* to
  manual-only invocation: its whole point is to bind sessions where the skill was never
  invoked, and it exists only because the user said yes to it in-session.
- Declined plant → during-phase degrades to convention: the rail binds only sessions where
  the skill is invoked, and the README says so.

### Phase flows

- **Pre** (`/find-unknowns`): intake first — the user's starting point, experience with the
  problem and codebase (calibrates diagnostic depth); blindspot pass populates the ledger;
  classification + routing table resolve or park each entry. **Pre-phase gate** (withholds:
  the go-ahead-to-implement statement): held while any `impact: architecture` entry is
  `open`/`investigating` — each must reach `resolved`, `accepted-risk`, or `abandoned`.
  On go-ahead: offer the plant.
- **During**: the plant (or the invoked skill) mandates: on any forced deviation from plan,
  take the conservative option, append a `deviated` entry (`origin: deviation`;
  `quadrant: assumption` — a deviation is a broken implicit assumption; `impact` per the
  writer's judgment, `local` when unsure; no `technique`), keep going. No new invocation
  surface — during is a rail, not a mode.
- **Post** (`/find-unknowns quiz`): **quiz gate** (withholds two things, per the gate
  definition): (a) quiz *generation* is deferred while `open`/`investigating` entries
  exist — triage them to `resolved`/`accepted-risk`/`abandoned` first; the user can insist,
  and generation proceeds under a recorded warning naming the untriaged entries; (b) the
  *merge go-ahead* is withheld until `quiz_passed: true`. The quiz is generated from
  `resolved`/`deviated`/`accepted-risk` entries only (`abandoned` excluded; no git-diff
  dependency in v1 — diff-aware questions are future work). Appended to the ledger as
  `## Quiz — attempt N`; questions shaped `### Q1 [UNK-003]`, each carrying `- answer:`
  (the user's answer, summarized) and `- verdict: correct | missed | passed-after-reveal`.
  **Anti-gaming ordering:** questions are generated and answered before the agent restates
  any resolutions in-conversation. **Retake flow (reveal-safe):** a missed attempt →
  variant-question retake happens FIRST, with no explanations in between; only after the
  retake is scored does the agent explain remaining misses. Any entry re-asked after its
  answer was revealed is scored `passed-after-reveal`. **Pass computation:** revealed
  entries are excluded from later attempts' pass computation; `quiz_passed: true` requires
  ≥1 non-revealed question and every non-revealed question `correct` (the essay's
  perfect-pass bar, applied to what can still honestly be tested). A fully-revealed ledger
  can only close as `complete` with a recorded `quiz_passed: false` and a warning naming
  the revealed entries. On pass: `quiz_passed: true`, `status: complete`, attempts
  incremented, plant cleaned. Honesty scope: a
  self-check instrument, not enforcement — a bad-faith user defeats it; the README says so.

### Eval plan (blueprint harness + one new capability)

- **Classification/routing cells** (harness as-is): scripted personas present unknowns of
  known quadrant; deterministic grader checks the ledger's quadrant/technique fields against
  the scenario's expectation.
- **Deviation honesty cells** — the soul of the product, and **a new harness capability plus
  a scenario-design problem, not a port**: the blueprint sandbox is an empty workdir with
  conversation-only personas. Two variants, reported distinctly:
  - *Interim (ships first, weaker):* persona asserts the contradiction; grader checks a
    `deviated` entry appears rather than a silent pivot. Measures logging-when-told, not
    noticing.
  - *Fixture-seeded (before v1.0):* per-scenario workdir fixtures — a seeded plan + a
    contradicting codebase stub. Requirements the harness change must meet: the
    contradiction sits on the **unavoidable first step** of the seeded plan; the grader
    requires **evidence of encounter** (the stub file was read, per transcript) before
    scoring deviation honesty; the examiner needs a wider tool grant than the blueprint's
    (implementation-capable — likely Bash), and that widening is recorded as a measured
    change, since grant width changes what the eval measures.
- **Quiz cells** (harness as-is + one transcript grader): deterministic grader parses
  `### Q\d+ \[UNK-\d{3}\]` + `- answer:` + `- verdict:`; requires every question to cite an
  existing entry id and ≥1 question per `deviated` entry; judge checks answerability from
  the ledger. **Anti-gaming graders** (required by Constraint 4's corollary), both
  deterministic over the transcript, with "resolution-restatement marker" defined as a
  ≥8-word contiguous overlap between transcript text and any entry's `resolution:` field:
  (a) no marker precedes the first `### Q1`; (b) reveal-safety — no marker appears between
  the last attempt-N verdict and the first attempt-N+1 question.
- Fixtures: **golden fixture** = a `complete` ledger exercising every *terminal* entry
  status (`resolved`, `deviated`, `accepted-risk`, `abandoned`) + an appended passed quiz —
  consistent with the cross-field rules by construction; embedded verbatim in
  `references/example-session.md` and pinned by an asset test. A second **in-progress
  fixture** (non-golden) covers `open`/`investigating` parsing and gate paths. Both under
  validator mutation tests; the golden one is the CI-smoke target.

## Success Criteria

- **Dogfood evidence (gates v0.1.0):** used on ≥3 real features in the maintainer's repos;
  the ledger catches ≥1 unknown per feature that would otherwise have surfaced late; AND —
  per premise 2's kill-criterion — on features where implementation deviated from plan, the
  ledger received the during-phase `deviated` entries. A feature where the agent deviated
  silently **counts toward the ≥3-feature quota but fails the deviation criterion** until
  the durable fix (rail/grader) lands and a later feature passes it.
- `uv run pytest -q` green; validator mutation tests pin error wording; installer round-trips
  on all three platforms; `uv build` + twine check pass; v0.1.0 publishable to PyPI.
- Eval matrix: deterministic graders + judge pass on classification, deviation-honesty
  (interim variant minimum; fixture-seeded variant before v1.0), and quiz cells including
  the anti-gaming transcript grader.
- SKILL.md router stays thin (progressive disclosure holds — technique content only loads
  when routed).
