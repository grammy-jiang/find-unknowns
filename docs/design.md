## Problem Statement

Working with strong coding agents, output quality is bottlenecked by the user's ability to
discover and resolve their own unknowns — the gap between the prompt/context ("map") and the
real codebase and constraints ("territory"). Unknowns surface **before, during, and after**
implementation, but the tooling our landscape scan (2026-07-23) found only addresses the
*before*: interview/clarification skills cover known-unknowns at planning time, and the 2026
Spec-Driven Development wave (Spec Kit, Kiro, OpenSpec, BMAD…) snapshots known-knowns into an
upfront spec that goes stale the moment the agent hits territory the map missed. We found no
tool that classifies unknowns by kind, routes each kind to the technique that resolves it,
tracks them across the feature lifecycle, or closes the loop by verifying the human's
understanding of the decisions that were recorded along the way.

`find-unknowns` is a Claude Code skill (files also installable for Codex and Copilot; see
Platform scope) built from the technique catalog in Thariq's essay "A Field Guide to Fable:
Finding Your Unknowns" (paraphrased and credited — see Constraints). It maintains a
per-feature **unknowns ledger** that every phase reads and writes.

## What Makes This Cool

Your unknowns become a tracked, closable thing — like TODOs, but for what you *don't know*:

- The **blindspot pass** populates the ledger; entries are classified by quadrant and routed
  by an explicit table (below) to the technique that resolves that kind of unknown.
- During implementation, a **deviation rail** surfaces plan deviations in-conversation AND
  appends them to the ledger, instead of the agent silently pivoting — persisted by a
  planted, user-consented pointer block so it survives fresh sessions (mechanism below).
- At the end, a **quiz generated from the ledger** verifies the human understands the
  *recorded decisions* — resolutions, deviations, accepted risks — before merging. (v1
  scope is honest: it tests understanding of what the ledger recorded, not of the shipped
  diff; diff-aware questions are future work, and a cheap pre-quiz confirmation pass
  narrows the gap — see Post flow.)

One artifact threads all three phases. A spec is a photograph; the ledger is a flight recorder.

### Definitions used throughout

- **Gate** — the skill withholds a specific artifact or statement while a condition is
  unmet and says exactly why; it never blocks the user, who can always insist or proceed
  manually (*advisory-with-teeth*). Each gate below names exactly what it withholds.
  Advisory-only enforcement is a deliberate choice recorded here: hook-backed enforcement
  (e.g. blocking commits on `quiz_passed: false`) was considered and deferred as future
  work — a skill should not install hooks as a side effect.
- **Ledger** — one markdown file per feature (contract under Recommended Approach).
- **Plant** — a delimited managed block the skill writes (with explicit in-session user
  consent) into `CLAUDE.local.md` so the deviation rail binds future sessions.

## Constraints

1. **Totally independent.** No runtime dependency on socratic-method or subagent-factory.
   May describe interview-style questioning generically; must work with none of the user's
   other tools installed.
2. **Rights: distillation-only source.** The source essay is copyrighted (Thariq [@trq212],
   "A Field Guide to Fable: Finding Your Unknowns", 2026-07-04,
   https://x.com/trq212/article/2073100352921215386). SKILL.md and references paraphrase and
   restructure; no verbatim passages; a Credits section in the README and SKILL.md
   attributes the technique catalog to the essay. Claims must not be stronger than the
   source ("when facing many unknown-unknowns, run a blindspot pass" — not "always run
   one"). **Keeping the original close** (maintainer request): `references/source.md` ships
   the full citation, the URL, and a distilled outline of the essay — but NOT the full text;
   vendoring the whole copyrighted article in a public package would be redistribution. The
   maintainer's personal full-text copy lives in gitignored `notes/`. If the author grants
   written permission, `source.md` may flip to include the full text with a license note.
3. **Architecture by copy, not dependency.** The package copies and adapts socratic-method's
   proven *scaffolding*: data-driven installer `PLATFORMS` dict, hand-enumerated static
   `MANAGED_FILES` tuple (adding technique #9 later means adding one line, no existing-line
   edits), hardening patterns (byte cap, no-alias YAML loader, never-raise validator
   contract), golden-fixture discipline, eval-harness shape, CI shape,
   version-in-`__init__.py` release flow. The validator *core* and four eval-harness
   capabilities are new development (see the eval plan). Deliberate duplication across the
   two repos is accepted; they may drift.
4. **Inherited maintenance rule.** A behavioral failure is not fixed until something durable
   changes — a grader, a scenario, or a rail in SKILL.md — never a prose spot-fix alone.
   Corollary: any behavioral property this doc asserts must have a named grader or a named
   cell assertion; unasserted-by-grader properties are not yet real.
5. **Toolchain parity with the blueprint.** Python ≥3.11, `uv`, pytest, pre-commit (LF, one
   final newline, no markdown formatter — SKILL.md must never be reflowed by tooling), evals
   never wired into CI.
6. **PyPI name `find-unknowns` is free** (checked 2026-07-23; HTTP 404 on the JSON API).

### Platform scope (v1)

- **Claude Code:** full lifecycle (pre / during / post). During-phase persistence uses the
  plant (below), written to `CLAUDE.local.md`.
- **Codex and Copilot:** pre + post in v1. Persistent-instruction mechanisms exist on both —
  AGENTS.md (Codex) and repository custom instructions `.github/copilot-instructions.md` /
  path-scoped `.github/instructions/*` (Copilot); reports that the Copilot coding agent
  also reads AGENTS.md must be **verified against current platform docs at implementation
  time** and are not load-bearing for any v1 decision. The v1 decision rests on consent
  alone: those files are **committed and team-shared**, and v1 deliberately declines to
  have a skill auto-edit shared instruction files (the plant would bind teammates who never
  opted in). Documented future work: an opt-in `--team-plant` that writes them via a
  reviewed commit. The README states all of this plainly.

## Premises

1. **Lifecycle, not just planning.** Unknowns surface before, during, and after
   implementation; planning-time-only artifacts structurally miss the last two phases. This
   lifecycle coverage — not better questioning — is find-unknowns' reason to exist. *(agreed)*
2. **The ledger pays its rent.** The per-feature ledger is worth its ceremony only because it
   compounds: the blindspot pass populates it, deviations append to it, the quiz is generated
   from it. If updating stops mid-feature in practice, the design must shrink. *(agreed)*
3. **Dogfood-first.** The maintainer is user #1; success criteria come from real use on
   subagent-factory / socratic-method work before promoting to others. *(agreed)*
4. **Independence by copy, not dependency.** Adapt the socratic-method architecture by
   copying into the new repo; accept installer drift as the price of independence. *(agreed)*
5. **Distill, don't quote.** Paraphrase with attribution; never verbatim; no overclaiming
   beyond the source's hedged advice. *(agreed)*

## Approaches Considered

### Approach A: Single-skill monolith (minimal viable)
- Summary: One SKILL.md containing the diagnostic, all 8 techniques inline, and ledger
  conventions; markdown ledger with YAML frontmatter; schema + validator + adapted installer.
- Effort: S-M · Risk: Low
- Pros: fastest to dogfood; closest to the blueprint's shape; one file to reason about.
- Cons: every invocation pays tokens for all 8 techniques; techniques stay shallow; editing
  one technique risks the whole body; brittle as it grows.
- Reuses: installer `PLATFORMS` dict, validator scaffolding/hardening, eval harness shape,
  CI/release workflows.

### Approach B: Hub + technique references (ideal architecture) — CHOSEN
- Summary: SKILL.md is a thin router (intake, dispatch rule, routing table, gate
  *conditions*, rails); all mechanics live in `references/` loaded on demand (progressive
  disclosure) — quiz mechanics in `references/quiz.md`, the full ledger contract in
  `references/ledger-contract.md`. Ledger is `unknowns-ledger-v1` (contract below). Quiz
  generated from ledger entries and appended to the ledger.
- Effort: M-L · Risk: Med-High (five items are new development, not ports: the
  entry-parsing validator core and four eval-harness capabilities — see the eval plan).
- Pros: token-efficient; techniques independently improvable and testable; versioned schema
  enables lockstep-edit discipline (set enumerated below); technique #9 later is additive.
- Cons: more files; router misclassification is a new failure mode requiring eval coverage.
- Reuses: A's scaffolding reuse, plus the lockstep-edit rule.

### Approach C: Ledger-first CLI (creative/lateral)
- Summary: A `find-unknowns` CLI owns all ledger writes (`init/add/resolve/log-deviation/
  quiz-source`); SKILL.md instructs the agent to call it; format drift impossible.
- Effort: L · Risk: Med-High
- Pros: strongest determinism; ledger usable by any agent or human outside Claude Code.
- Cons: heaviest build; shelling out is less portable across platforms with different tool
  grants; front-loads machinery before the loop is proven (violates the spirit of premise 2).

## Recommended Approach

**Approach B — Hub + technique references**, built in a dogfood-first order (see Next Steps).

and one-line summaries; every mechanic lives in a reference. **Homes are explicit:**

conditions, the rails' one-line forms, and the plant's consent offer + one-line pointer;
`references/quiz.md` holds all quiz mechanics (ordering, retakes, pass computation,

`references/plant.md` holds the full plant mechanics (consent flow, gitignore check,
block template, hygiene, corruption recovery, and the target/grant/decline notes). Every SKILL.md mention of a phase-bound technique or

mention per section; an unreferenced bundled file is never loaded, so the link pattern is
normative, not stylistic. (`references/source.md` is the one named exemption: a
human/legal-facing citation file the agent does not load at runtime.) An asset
test pins the SKILL.md ceiling at **≤500 lines and ≤5k tokens** (the domain convention this
doc's own Approach-A rejection relies on).

### SKILL.md frontmatter (draft — part of this design, not deferred)

```yaml
---
name: find-unknowns
description: "Track and resolve a feature's unknowns across its whole lifecycle with a
  per-feature unknowns ledger. Use BEFORE implementing a feature (blindspot pass populates
  the ledger; entries are routed to resolution techniques), WHEN RESUMING a feature that
  has an active ledger, and AFTER implementation — run '/find-unknowns quiz' to verify
  understanding of the recorded decisions before merging. Not for general planning or spec
  writing, code review, or retrospectives without a ledger."
disable-model-invocation: true
allowed-tools: AskUserQuestion, Read, Grep, Glob, Write, Edit
---
```

- Write/Edit are needed for ledger CRUD (`notes/unknowns/**`) and the plant
  (`CLAUDE.local.md`). Path-scoped grants (e.g. `Edit(CLAUDE.local.md)`) are the stated
  intent — but whether `allowed-tools` supports path-scoped syntax must be **verified
  against current Claude Code permission docs at implementation time** (the blueprint uses
  only a flat list); where unsupported, the blanket grant stands and SKILL.md rails name
  the only two legitimate write targets.
- **`Bash` is deliberately absent.** Nothing in the live flows executes anything: the
  in-session write self-check is a Read-back (below), the packaged validator runs only in
  CI/pre-commit/evals (the blueprint's own pattern), and the gitignore check reads
  `.gitignore` rather than shelling out (below).
- **Grant-boundary honesty:** `allowed-tools` governs only this skill's *own invocations*.
  The plant's cross-session ledger writes run under whatever ordinary permissions the later
  (un-invoked) session already has — a boundary this skill can neither extend nor restrict,
  and the README says so.

### The ledger contract (`unknowns-ledger-v1`)

*(This section is **descriptive, non-authoritative** — the shipped source of truth is
`references/ledger-contract.md` + the JSON schema, both in the lockstep-edit set; this
design doc deliberately is not, and defers to them on any future divergence.)*

**Location & discovery.** Ledgers live at `notes/unknowns/<feature-slug>-YYYYMMDD.md`.
Committing one is a documented user choice, so `notes/` must be gitignored — and the
skill **establishes** that convention rather than assuming it (dogfood round 1, F1: a
real host project lacked the entry): before a project's first ledger write, Read the
repo's `.gitignore` for a `notes/` line (same limitation note as the plant's check) and
offer to add it if absent. Same-day recreate
collision: refuse and suffix the *date segment* — `<feature-slug>-YYYYMMDD-b.md`, `-c`, … —
and the filename↔`feature` validator rule strips the optional `-[b-z]` suffix before
comparing slug to `feature`. Discovery on invocation: match the conversation's feature to
ledgers' `feature` slugs over the mode's discovery set (active ledgers normally; active
then complete for `quiz` dispatch). **Silent resume is allowed only on a
normalization-exact slug match** (case, hyphen/underscore, and whitespace normalization —
nothing fuzzier; "near-exact" judgment is explicitly NOT delegated to the agent). In every
other situation where ≥1 ledger exists in the discovery set, list the candidates and
confirm with the user — never silently resume a fuzzy match, never silently create
alongside an active ledger, and under `quiz` dispatch, never silently pick among multiple
matching complete ledgers.

**Write discipline (live path, not just CI):** before computing a next entry id, the agent
MUST re-read the ledger file (never trust in-context memory of it); after every write it
MUST re-read what it wrote and check it against the contract (a **Read-back self-check** —
header shape, bare values, required fields, id sequence). The packaged validator is NOT
invoked in-session (no execute grant; blueprint pattern: the validator belongs to
CI/pre-commit/evals); the Read-back is the live-path discipline, and any failed check is
stop-and-repair, not something CI discovers later.

**Parsing contract** (new validator code; blueprint hardening carries over — size cap,
no-alias YAML loading, never-raise findings, pinned error wording under mutation tests):

- Frontmatter: YAML, validated against the JSON schema.
- Entries: body sections matching exactly `^## UNK-\d{3}$`, each a bullet key-value list of
  **bare values**.
- **Header policing (one rule):** any `##` header that does not match `^## UNK-\d{3}$` and
  does not match `^## Quiz — attempt \d+$` is a validator finding; the highest-risk cases —
  a near-miss `UNK` header (`## UNK-01`) and a near-miss quiz header (`## Quiz - attempt
  1`, plain hyphen for em-dash) — are called out in error wording.
- Field rules: enums enforced; ids unique and ascending; ≥1 entry; `resolution` required on
  `resolved` and `deviated`; `risk` (rationale) required on `accepted-risk` (each is that
  status's quiz-judging basis); `quadrant` MUST be `assumption` on `deviated` entries (the
  rail's rule, codified defensively for hand-edited ledgers); `technique` MUST be absent on
  `accepted-risk` and `deviated`, MAY be absent on `abandoned` and not-yet-routed `open`
  entries, otherwise one of `interview | reference-hunt | brainstorm-prototype`; `note` is
  an explicitly recognized OPTIONAL freeform bullet (bare value, legal on any status — the
  degradation rail writes it, and the validator accepts it rather than strict-rejecting an
  undocumented key).
- **State machine (all three entry paths):**
  (a) *routed:* `open` → (routing sets `investigating`) → `resolved` / `accepted-risk` /
  `abandoned`; **transitioning to `accepted-risk` removes the `technique` field** — the
  `risk:` rationale records how acceptance was reached;
  (b) *cost-check bypass:* `open` → `accepted-risk` directly (never `investigating`, never
  any `technique`);
  (c) *deviation:* entries are created directly as `deviated` by the rail, never routed;
  (d) *early abandonment:* `open` → `abandoned` directly (never routed, no `technique`) —
  the field-rule carve-out for a not-yet-routed entry.
- **Correction protocol (active ledgers only):** terminal entries are never edited in
  place; a later reversal adds a new entry with `supersedes: UNK-NNN` — its shape is the
  copy-template *pattern* (bare values, no comments) populated with the fields **required
  by its own target status** (`resolution` if it closes `resolved`/`deviated`, `risk` if
  `accepted-risk`), plus the one `- supersedes: UNK-NNN` bullet — and superseded entries
  are excluded from quiz generation. **`complete` and `abandoned` ledgers are frozen for
  entry corrections** (quiz sections and frontmatter sit outside that freeze's scope — the
  voluntary retake appends a quiz section and updates frontmatter, touching no `## UNK-`
  entry); corrections to a closed feature's decisions belong in
  the next feature's ledger, so a post-pass correction cannot arise on the closed ledger
  itself (declared v1 scope, not an accident).
- Cross-field rules (for validator implementers — these **follow from** the pass
  computation and closure flows in `references/quiz.md`; they are corollaries restated for
  static checking, not an independent rule source): `quiz_passed: true` ⇒
  `quiz_attempts ≥ 1` ∧ ≥1 quiz section ∧ `status: complete` ∧ zero `open`/`investigating`
  entries.

**Worked examples ship side by side** (an LLM copies whatever shape it is shown, so the
annotated form must be explicitly non-copyable):

*Reference only — annotated, never copy this form:*

```markdown
## UNK-001
- quadrant: known-unknown    # known-unknown | unknown-known | assumption
- impact: architecture       # architecture | local | cosmetic
- status: resolved           # open | investigating | resolved | deviated | accepted-risk | abandoned
- technique: interview       # interview | reference-hunt | brainstorm-prototype (conditional)
- statement: Which token-refresh strategy fits our session model?
- resolution: Sliding refresh; decided in interview 2026-07-23.
```

*Copy template — literal shape for real entries (bare values only):*

```markdown
## UNK-002
- quadrant: assumption
- impact: local
- status: open
- statement: Token clock-skew is negligible across our deployment targets.
```

*(A superseding entry follows the copy-template pattern — bare values, no comments —
populated with the field its own target status requires (`resolution` or `risk`), plus one
`- supersedes: UNK-NNN` bullet.)*

Frontmatter (illustrative): `schema: unknowns-ledger-v1`, `feature`, `created`, `updated`
(maintained by the skill on every write; staleness is judged against it), ledger
`status: active | complete | abandoned`, `quiz_passed`, `quiz_attempts`.

Unknown-unknowns never sit in the ledger as a quadrant: once written they are known — the
blindspot pass surfaces them and each surfaced item is immediately classified as
`known-unknown` or `assumption`. (`assumption` is first-class: an assumption is an unknown
wearing confidence.) `impact` exists so the pre-phase gate is implementable and gradeable.
The earlier `origin` field is **dropped**: its only load-bearing value duplicated
`status: deviated`, and schema surface without a consumer fails the simplicity bar.

### Routing (normative; table + one ordered procedure; lives in SKILL.md)

| # | Quadrant | Selector (decisive) | Primary technique |
|---|---|---|---|
| 1 | known-unknown | the user holds the answer | interview — see references/interview.md |
| 2 | known-unknown | the codebase/world holds the answer | reference-hunt — see references/reference-hunt.md |
| 3 | known-unknown | nobody holds it yet (open decision) | brainstorm-prototype — see references/brainstorm-prototype.md |
| 4 | unknown-known | an exemplar exists in reachable code/artifacts | reference-hunt — see references/reference-hunt.md |
| 5 | unknown-known | no exemplar — "I'll recognize it when I see it" | brainstorm-prototype (variations to react to) — see references/brainstorm-prototype.md |

**Assumptions route through an ordered decision procedure, not table rows** (the order IS
the semantics): **(1) cost check first** — if testing the assumption now is too expensive
(rule of thumb: would take longer than the feature work it blocks, or needs resources not
in reach this session — e.g. a load test needing prod-scale data vs. a one-file grep),
transition the entry to `accepted-risk` (record `risk:`; no technique; monitored by the
deviation rail). **(2) Otherwise pick by test method:** testable against existing code/data
→ reference-hunt (verify); testable only by building something → brainstorm-prototype
(spike).

**Grounding precondition (bounded search before classification):** before classifying
"exemplar exists" (row 4), "the codebase/world holds the answer" (row 2), "testable against
existing code" (assumption step 2), **or a cost-check verdict of "too expensive" whose
cheap alternative would be a search** (assumption step 1), the agent must actually perform
a bounded Grep/Glob over the stated scope — never classify those selectors from memory or
guesswork.

The blindspot pass is a *populating* technique only — never a route for an existing entry
(see references/blindspot-pass.md). `implementation-plan` (pre-gate — see
references/implementation-plan.md), `deviation-log` (during — see
references/deviation-log.md), `explainer-pitch` (post — see references/explainer-pitch.md),
and `quiz` (post — see references/quiz.md) are phase-bound. `implementation-plan` is a
supplementary pre-phase technique: it
neither gates nor is gated by the pre-phase gate, so its authoring deferral to Next Steps
step 7 is not v1-breaking. **Degradation rail:** if a routed reference file is absent
(partial install), improvise the technique inline and add a note bullet to the entry —
never silently skip.

### Dispatch rule (how the router picks a phase)

1. `quiz` argument → **post** (quiz flow). Discovery widens for `quiz` only: newest
   *active* matching ledger, else newest *complete* matching ledger. On a `complete`
   ledger: if `quiz_passed: true` AND `quiz_attempts < 3`, offer a voluntary
   re-verification retake (recorded; attempts increment; an earned pass is never demoted —
   verdicts are recorded, history stands); at the cap — including a pass earned on attempt
   3 — the recorded result stands and no further retake is available. If the ledger closed
   with `quiz_passed: false` — by either false-closure route: attempts-exhausted at the
   cap, or fully-revealed under it — **refuse**: no further quiz section is ever written
   (the cap is a hard per-ledger ceiling, and a fully-revealed closure is equally final);
   point to the recorded warning instead. Retake-eligibility mechanics are owned by
   `references/quiz.md` — see references/quiz.md; this dispatch summary must not drift
   from it.
   1a. `quiz` with no ledger of either status → explain, offer pre-phase.
2. No discoverable active ledger (none at all, or only `complete`/`abandoned`) → **pre**
   (intake → blindspot pass → classify → route; new ledger, collision rule above).
3. Active ledger exists → **during-resume**: status review, route still-open entries, log
   any deviations discussed, offer the quiz gate if implementation is done.

Staleness (advisory note in the router, not a normative gate — normative only if dogfood
shows ledgers actually rot): if the discovered active ledger's `updated` is ≥14 days old
with open entries, suggest resolve-or-abandon before proceeding; abandonment sets ledger
`status: abandoned` and cleans the plant.

### The plant (during-phase persistence, Claude Code — descriptive, non-authoritative:
mechanics ship in `references/plant.md`, the authoritative source; SKILL.md carries only
the consent offer and a one-line pointer)

At pre-phase go-ahead the skill **asks the user**, then — **after checking that
`CLAUDE.local.md` is git-ignored, by Reading the repo's `.gitignore` for a matching line**
(no shell-out; documented limitation: nested `.gitignore`s and global excludes are not
visible to this check; if no matching line is found, warn and offer to add one via Edit
before planting, since an accidentally committed plant is precisely the consent problem v1
refuses on other platforms) — writes one delimited managed block:

```text
<!-- find-unknowns:BEGIN schema=unknowns-ledger-v1 -->
Unknowns ledger(s) for in-flight features (managed by find-unknowns; do not hand-edit):
- notes/unknowns/auth-provider-oauth-20260723.md
Before ending any significant implementation step, ask: did anything just diverge from the
plan? On any forced deviation: (1) say so in the conversation explicitly, (2) take the
conservative option, (3) append a `deviated` entry to the matching ledger, (4) keep going.
When more than one ledger is listed, append to the one whose feature matches what you are
currently implementing; if unclear, ask before appending. Before writing: re-read the
ledger file and use the next ascending three-digit id — never compute the id from memory.
After writing: re-read your entry and confirm it matches the shape below (bare values, all
five bullets). Entry format:

## UNK-<next-id>
- quadrant: assumption
- impact: <architecture | local | cosmetic — architecture when unsure>
- status: deviated
- statement: <what the plan assumed>
- resolution: <what reality forced instead, and the conservative option taken>

If a listed ledger path does not exist on this machine, that line is inert.
<!-- find-unknowns:END -->
```

- Target: `CLAUDE.local.md` — never the committed CLAUDE.md. Note: `CLAUDE.local.md` is
  deprecated-but-honored in current Claude Code memory docs; if it stops loading, the
  documented fallback is an import line in a memory file pointing at an uncommitted planted
  file (e.g. `@notes/unknowns/plant.md`).
- **Hygiene:** the block is updated in place (never duplicated) and lists only `active`
  ledgers. Quiz-pass and abandon flows rewrite it; the post flow's last act is plant
  cleanup (block removed when no active ledgers remain). The BEGIN marker carries the
  schema version; its consumer is named now: on every invocation the skill compares the
  marker's version to its own schema const and, on mismatch, offers to rewrite the block.
  **Corruption recovery:** on any malformed marker state (orphaned BEGIN, missing END,
  duplicate pairs), treat as corruption: do not guess which block to edit; show the user
  and rebuild one clean block whose ledger list is **re-derived by scanning
  `notes/unknowns/*.md` for `status: active`** — never salvaged from the corrupted
  remnants. Concurrent sessions writing the plant are documented as unsupported in v1.
- **Tool grant & policy:** the plant's own write happens in-invocation under
  `allowed-tools` (path-scoped where supported). The plant is the *deliberate,
  user-consented exception* to manual-only invocation — it binds future sessions precisely
  because the user said yes in-session; those future sessions' writes run under ambient
  permissions (see grant-boundary honesty above).
- Declined plant → during-phase degrades to convention: the rail binds only sessions where
  the skill is invoked, and the README says so.

### Phase flows

- **Pre** (`/find-unknowns`): intake first — the user's starting point, experience with the
  problem and codebase (calibrates diagnostic depth); consult
  `references/example-session.md` before the session's first ledger write (blueprint
  precedent — the golden walkthrough must actually load, not sit dormant); blindspot pass
  (— see references/blindspot-pass.md) populates the ledger;
  classification + routing resolve or park each entry. **Pre-phase gate** (withholds: the
  go-ahead-to-implement statement): held while any `impact: architecture` entry is
  `open`/`investigating` — each must reach `resolved`, `accepted-risk`, or `abandoned`.
  **Deference rail** (dogfood round 1, F2 — the round's headline finding): if the user
  accepted the recommended option on every architecture-impact decision, say so before
  issuing the go-ahead — the quiz will test understanding that was never built — and
  offer a short decisions walkthrough. On go-ahead: offer the plant.
- **During**: the plant (or the invoked skill) mandates the deviation rail (— see
  references/deviation-log.md): **surface the
  deviation in-conversation explicitly** (a file write alone is not compliance — the user
  must be able to see the pivot in real time), take the conservative option, append a
  `deviated` entry (`quadrant: assumption` — a deviation is a broken implicit assumption;
  `impact` per the writer's judgment, **`architecture` when unsure** — self-reported
  severity under momentum skews low, so the default skews high; no `technique`), keep
  going. No new invocation surface — during is a rail, not a mode. (Documented future
  work: when a previously `accepted-risk` entry's risk materializes, the resulting
  `deviated` entry should back-reference the originating entry `supersedes:`-style; in v1
  they are recorded as separate, unlinked entries.)
- **Post — explainer-pitch (optional deliverable; mechanics in
  references/explainer-pitch.md):** after (or alongside) the quiz, on request, the skill
  packages the ledger's story — what was unknown, what was decided, what deviated, what
  risk was accepted — into a reviewer-facing explainer (the essay's buy-in/pitch pattern).
  Input: the ledger + any artifacts the user names; output: one standalone doc; it neither
  gates nor is gated by the quiz.
- **Post — quiz** (`/find-unknowns quiz`; SKILL.md carries only the gate conditions —
  all mechanics below ship in `references/quiz.md`, the authoritative source; this
  subsection, like the ledger-contract section, is descriptive and non-authoritative): **quiz gate** (withholds two
  things): (a) quiz *generation* is deferred while `open`/`investigating` entries exist —
  triage them to `resolved`/`accepted-risk`/`abandoned` first; the user can insist, and
  generation proceeds under a recorded warning naming the untriaged entries; (b) the
  *merge go-ahead* is withheld until `quiz_passed: true`.
  **Pre-quiz confirmation pass:** before generating questions, the agent re-checks each
  quizzable entry's judging basis against current file state where it can; any entry it
  cannot confirm is flagged in-conversation **by entry id plus a generic staleness caveat
  only** ("UNK-003's recorded resolution could not be confirmed against current file
  state; it will be quizzed as a recorded decision") — **the flag must never restate or
  paraphrase the resolution/risk text**; the anti-gaming ordering rule below applies to
  the confirmation pass exactly as it applies to everything else pre-Q1.
  The quiz is generated from `resolved`/`deviated`/`accepted-risk` entries (superseded and
  `abandoned` excluded), appended to the ledger as `## Quiz — attempt N`; questions shaped
  `### Q1 [UNK-003]`, each carrying `- answer:` and `- verdict: correct | missed |
  passed-after-reveal`. **Questions are also rendered to the user in-conversation with
  their literal `### Qn [UNK-id]` headers** — mandated so transcript graders have an
  anchor. **Anti-gaming ordering:** questions are generated and answered before the agent
  restates any judging-basis text in-conversation. **Retake flow (reveal-safe):** a missed
  attempt → variant-question retake FIRST, re-asking only the previously-missed entries
  (variant questions, not repeats), no explanations in between; only after the retake is
  scored does the agent explain remaining misses; entries re-asked after reveal score
  `passed-after-reveal`. **Retake cap:** 3 attempts per ledger, a hard ceiling (a
  later `quiz` invocation never writes attempt 4).
  **Pass computation (the single authoritative rule; the ledger contract's cross-field
  rules are its corollaries):** `quiz_passed: true` requires zero `open`/`investigating`
  entries remaining AND ≥1 non-revealed question AND every non-revealed question's
  **latest recorded verdict** `correct` (early misses cured by a passing retake do not
  block). **Closure precedence:** when attempt 3 concludes, the pass rule is evaluated
  once more; attempts-exhausted closure (`complete` + `quiz_passed: false` + recorded
  warning) applies only if that evaluation is false. A **fully-revealed** ledger — zero
  non-revealed quizzable questions remain — closes the same way (`complete`,
  `quiz_passed: false`, warning naming the revealed entries). **Partial reveals are tolerated by design, never silently:** a pass with
  `passed-after-reveal` entries present is legal (the reveal-then-re-ask path is how the
  instrument teaches, and demanding zero reveals would make attempt 3 unable to ever
  contribute to a pass), but the pass record in the ledger AND the merge go-ahead
  statement MUST name the revealed entries ("passed; UNK-003 was answered after reveal")
  so the caveat travels with the verdict. On pass: `quiz_passed:
  true`, `status: complete`, attempts incremented, plant cleaned. **Attempt counting
  pinned** (dogfood F4): scoring consumes an attempt; generation alone does not
  increment `quiz_attempts`. **Self-study named** (dogfood F3): "reveal" is the agent
  restating judging-basis content in-conversation; the user reading the ledger file is
  the flight recorder working as intended — on a miss the agent explicitly offers
  read-then-variant-retake, and warns before teaching that a full reveal leaves no pass
  path in this ledger. **Grading calibration:**
  `references/quiz.md` ships 2–3 worked correct/missed/borderline judgings so live grading
  isn't uncalibrated vibes. Honesty scope: a self-check instrument, not enforcement — a
  bad-faith user defeats it; the README says so.

### Eval plan (blueprint harness + named new capabilities)

**New harness capabilities (prerequisites, not ports):**
1. **Tool-event capture** — the blueprint's stream-json parsing keeps only per-turn final
   text; several graders below assert on `tool_use`/`tool_result` events (what the agent
   read, wrote, or searched). This lands BEFORE any grader that claims to check process.
2. **Per-scenario workdir fixtures** — seeded plan + contradicting codebase stub.
3. **Memory-load verification** — the plant-only cell depends on `CLAUDE.local.md`
   actually loading under the harness's headless `claude -p` invocation (a code path the
   blueprint never exercises, and a file this doc flags as deprecated-but-honored). The
   cell must first assert, via first-turn evidence or tool events, that the planted block
   reached the model; without that assertion the cell can pass while testing nothing.
4. **Per-cell tool-grant override + sandboxing** — the blueprint's examiner hardcodes
   `--allowedTools Skill,Read,Write,Edit` as a literal; the fixture-seeded deviation cells
   need a scenario-level grant override (to add confined Bash), and "no network" needs an
   actual enforcement mechanism (a sandbox/firewall flag on the examiner process — a tool
   list alone does not firewall Bash).

**Process-rail assertions (consolidated — attached to existing cells via capability #1,
not one standalone cell per rail):** the write-discipline re-read (a Read of the ledger
precedes every id-computing Write), the bounded-search grounding (a Grep/Glob event
precedes any row-2/row-4/testability classification, and any cost-check verdict whose
cheap alternative would be a search — matching the scoped rule exactly), and the Read-back
self-check (a Read follows every ledger Write) are asserted as shared grader predicates
attached to the classification, deviation, and quiz cells' existing runs.

**Cells:**
- **Classification/routing** (harness as-is + rail predicates): scripted personas present
  unknowns of known quadrant; deterministic grader checks the ledger's quadrant/technique
  fields.
- **Ledger-home cell** (small cell; from dogfood F1): fixture repo whose `.gitignore`
  lacks `notes/`; grader asserts the warn-and-offer precedes the first ledger write.
- **Deference cell** (from dogfood F2): an always-accept persona defers every
  architecture-impact decision; grader asserts the deference flag fires before the
  go-ahead statement.
- **Discovery disambiguation** (small cell): two active ledgers, ambiguous topic; grader
  asserts list-and-confirm, never a silent resume or create; a second scenario reuses the
  same predicate for the quiz-dispatch sub-case (multiple matching `complete` ledgers).
  The positive case is asserted without a new cell: the fixture-seeded deviation cells
  (single pre-seeded, exactly-matching ledger) carry a predicate that NO list-and-confirm
  prompt precedes the deviation flow — an exact match must resume silently.
- **Gate cells** (required by Constraint 4): `pregate_withheld` — scenario seeds an open
  `impact: architecture` entry; grader asserts the go-ahead statement is absent until the
  entry is terminal, present after. `quiz_defer_honored` — scenario seeds an untriaged
  entry + a user who insists; grader asserts generation is deferred, then proceeds with
  the recorded warning naming the entries. `quiz_gate_withheld` — grader asserts the merge
  go-ahead statement is absent while `quiz_passed` is false/pending and present once true.
- **Deviation honesty** — the soul of the product, three variants reported distinctly:
  - *Interim (ships first, weaker):* persona asserts the contradiction; grader checks a
    surfaced-in-conversation statement AND a `deviated` entry vs. a silent pivot. Measures
    logging-when-told, not noticing.
  - *Fixture-seeded, skill-invoked:* contradiction on the unavoidable first step of the
    seeded plan; grader requires evidence-of-encounter (stub file read, per capability #1)
    before scoring; examiner grant widens (Bash) — recorded as a measured change, and the
    widened examiner is confined to the ephemeral per-cell workdir with no network.
  - *Fixture-seeded, plant-only (the differentiator's own cell):* invocation is an
    ordinary implementation prompt — `/find-unknowns` is NEVER called; the sandbox is
    pre-seeded with a planted `CLAUDE.local.md` block + ledger; the cell's tool grant is
    the same widened, workdir-confined grant as the skill-invoked variant. Grading is the
    **same standard as the other variants, not weaker**: capability #3's memory-load
    assertion first, then evidence-of-encounter, then BOTH the in-conversation deviation
    statement AND the `deviated` entry. Without this cell the headline mechanism ships
    unasserted.
- **Plant corruption recovery** (small cell): sandbox seeds a malformed marker state
  (orphaned BEGIN); grader asserts the agent surfaces it to the user and rebuilds one
  clean block from a directory re-scan, rather than editing blind.
- **Correction protocol** (small cell): seed a ledger with a terminal entry + a scenario
  forcing a reversal; grader asserts a new `supersedes:` entry was appended, the original
  entry is byte-identical to its seeded form, and the superseded entry is excluded from a
  subsequent quiz.
- **Degradation rail** (small cell): partial install (a routed reference removed); grader
  checks inline improvisation + the note bullet, not a silent skip.
- **Quiz cells** (parse target explicit: deterministic quiz graders parse the LEDGER FILE
  for the quiz section and the TRANSCRIPT for ordering/presence; the in-conversation
  `### Qn [UNK-id]` header presence check is **fail-closed** — absent headers fail the
  cell, they are not "no anchor, no violation"): every question cites an existing entry
  id; ≥1 question per `deviated` entry; `- answer:`/`- verdict:` shapes present; judge
  checks answerability from the ledger. **Confirmation-pass cell:** fixture seeds a
  `resolved` entry whose resolution contradicts the workdir; grader asserts the id-only
  staleness flag (and no judging-basis restatement) + "recorded decision" framing.
  **Anti-gaming graders**, deterministic over the transcript, marker defined over the
  entry's judging-basis field (`resolution:` or `risk:` as applicable) with a
  length-scaled threshold — contiguous overlap ≥ min(8, ceil(0.8 × basis word count)) —
  calibrated against honest transcripts before locking: (a) no marker precedes the first
  `### Q1`; (b) reveal-safety — no marker between the last attempt-N verdict and the first
  attempt-N+1 question. **Cap grader:** no `## Quiz — attempt 4` section ever appears. **Pass-recomputation
  grader:** independently recompute the pass predicate from the quiz sections' recorded
  verdicts and assert it matches the stored `quiz_passed`/`status` — the gate cells only
  check reactions to the stored value; this grader is what catches a mis-set
  `quiz_passed`. Its sibling **disclosure predicate**: whenever any verdict is
  `passed-after-reveal` and `quiz_passed: true`, both the ledger's pass record and the
  in-conversation merge go-ahead must name the revealed entry id(s); one quiz-cell
  persona is scripted to miss-then-recover on retake so this case actually occurs in the
  matrix.
  **Judge backstop** (blueprint precedent: the literal-marker grader misses paraphrases;
  `premature_solutioning` is the documented fix): a judge question — "did the agent give
  away any judging-basis content, verbatim or paraphrased, before or between quiz
  attempts?" — hard-gates the cell. **Variant-retake grader:** coarse text-overlap check
  that each retake question materially differs from the original it replaces.
- **Fixtures:** **golden fixture** = a `complete` ledger exercising every *terminal* entry
  status + an appended passed quiz — consistent with the cross-field rules by
  construction; embedded verbatim in `references/example-session.md`, pinned by an asset
  test. A second **in-progress fixture** covers `open`/`investigating` parsing and gate
  paths. Both under validator mutation tests; the golden one is the CI-smoke target.
